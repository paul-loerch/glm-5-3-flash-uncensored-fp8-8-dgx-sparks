# Patches

Everything this recipe changes in vLLM, and why. For each change you get the problem, what the change does, how to switch it, what it does to numerics, what we measured, and where upstream stands.

The recipe serves **GLM-5.3-Flash FP8** (checkpoint `orcarouter/GLM-5.3-Flash-Uncensored-FP8`, revision `3cec42d6`) with **vLLM v0.32.0** at tensor parallel 8 across eight NVIDIA DGX Spark (GB10, sm_121) nodes joined by 100G RoCE, one rank per node, with MTP speculative decoding (2 draft tokens at batch size 1, 1 draft token at batch sizes 2-8) and a 1,048,576-token context. The base image is `vllm/vllm-openai:v0.32.0-aarch64@sha256:6ff5ff0ddf3658d2c2d677dac5ca2d4726ce0156b4371166d918181b210bd4bc` (vLLM commit `5df63a7203cd`, CUDA 13.0.2, FlashInfer 0.7.0.post1). Pin it by digest: every file hash the patches check is the hash of a file in that image.

## 1. Reading guide

### 1.1 Four kinds of change

| Kind | What | Where | Applies |
|---|---|---|---|
| Build-time bake, B1-B5 | source edits for sm_121 in vLLM and FlashInfer, plus a tuned MoE table | `image/Dockerfile`, `image/glm53_sm121_v032.py` | once, when the image is built |
| Runtime patches, 001-035 | 14 patch scripts that edit vLLM's Python files | `patches/NNN-*.sh`, `patches/entrypoint.sh` | at every container start; each, except 001, behind its own environment variable |
| Tool-parser plugin, T1 | a small vLLM plugin | `patches/plugins/glm45_auto_tool_parser.py` | loaded by vLLM through two flags |
| Configuration | flags and environment variables | `config/recipe.env` | only the settings that stand in for a patch are discussed (section 5) |

An earlier version of this recipe ran on the day-0 GLM-5.3-Flash image (vLLM `487ecf187`, built before the model was merged upstream) with 27 active patches. We call it the previous base. Patch numbers are kept from that version, so the gaps in the numbering are patches that upstream made unnecessary, that configuration replaced, or that were never shipped (sections 4 to 6). Numbers 004, 005 and 013 were never part of a shipped patch set; 007 and 008 were the DFlash2 patches, and 018 part B, 023 and 034 are named in section 6. Measurements from the previous base are labelled "measured on the previous base".

### 1.2 The hardware and the model in a few lines

- **GB10 (sm_121).** One GPU per node, about 121 GiB of unified memory, about 210-230 GB/s of weight-read bandwidth, 101,376 B of shared memory per block (some stock kernels want 128 KB), no GPUDirect RDMA.
- **Eight ranks over RoCE.** At TP=8 every layer ends in a network all-reduce. A decode step issues about 100 collectives, and they are latency-bound.
- **Host CPU.** Spinning waits keep performance cores at full clock (the CPU-cluster sensor, not the GPU, is the hottest thermal zone), and host-device syncs sit on the decode critical path.
- **The model.** 45 layers: 34 KDA layers (Kimi Delta Attention, linear attention with a constant-size recurrent state) and 11 NoPE multi-head-latent-attention (MLA) layers with DeepSeek-style sparse attention, in which a small "indexer" picks the top 2,048 tokens as 512 "pools" of 4 tokens (`index_kpool` = 4). 288 routed experts plus one shared expert, top-8. mHC hyper-connections (four parallel residual streams). One MTP (multi-token prediction) block, the draft model for speculative decoding: 2 draft tokens at batch size 1 and 1 draft token at batch sizes 2-8 (`num_speculative_tokens_per_batch_size`).
- **Terms.** TP, PP and DP are the tensor-, pipeline- and data-parallel sizes. A rank is one TP process, one per node; rank 0 also serves the API. M = tokens in one decode-time forward pass, drafts included. T = tokens in a prefill forward pass. Acceptance length = mean tokens produced per speculative step. TTFT = time to first token.

### 1.3 How the runtime patches are applied, and why that is safe

`patches/entrypoint.sh` runs every top-level `patches/NNN-*.sh` in numeric order inside each rank's container, printing `[recipe-entrypoint] applying <script>` before each, and then starts `vllm serve`. A script that exits non-zero makes it print `[recipe-entrypoint] FATAL: <script> failed`, and the container stops. The patch directory is mounted read-only, containers are created fresh at every start (the image is never modified), and the launcher refuses to start unless the directory is identical on every node.

1. **Vendored, not fetched.** Nothing is downloaded at boot.
2. **Pinned.** Each script checks the sha256 of every file it edits (the image's original, or the known result of an earlier patch), of its applier and of any module it installs. Files a patch only reads, but whose behaviour its argument depends on, are pinned too. Anything else is refused, so a different image stops the boot instead of being patched blindly.
3. **Anchored and atomic.** Every edit must match its anchor exactly once. Edits are computed in memory, compiled or parsed, written atomically and re-hashed; on any failure, or on TERM/INT/HUP, the original bytes are restored. Re-running is a no-op.
4. **Gated, one line each.** Except 001, which always applies and prints its own `[OK] busy_loop_s = ...` line, a patch is inert unless its environment variable is set. Each prints one `[OK] patch NNN in place (...)` line when it applies, or a `skipped` or `inert` line when it does not. Gates with a defined set of values refuse anything else, so a typo cannot silently disable a patch. Set the same variables on every rank: a rank that lacks a gate does not join the collectives the others enter.
5. **Self-tests at boot.** Patches that touch numerics or collectives check themselves on the real model: bit-exactness against the unpatched path, or error bounds against fp32/fp64, on every rank, then a vote over the CPU (gloo) group so no rank carries on alone. A failure either aborts the boot or leaves vLLM's own path in place with an `INACTIVE`, `DISABLED` or `FALLBACK` line; each section says which. Patches that change a rank's collective count also compare a configuration fingerprint across ranks.
6. **Checked before the first boot.** Each patch was run on CPU through its real applier on the real vLLM files, with planted faults ("mutants") that the checks had to catch, plus its apply, idempotency, refusal and rollback paths. Those checks use stand-ins for torch and CUDA; the boot self-tests are the check on the real hardware.

Install lines quote the words ACTIVE and INACTIVE, so when you check a boot automatically, count only the runtime `[patch-NNN] ... ACTIVE` lines that follow `all patches applied`.

### 1.4 What "numerics" means here

**Bit-exact** means that for the same inputs the patched path produces bitwise the same tensors as vLLM v0.32.0's own path, argued from the code (same operands, same order) and re-checked bitwise at boot or in a GPU test. **Changes numerics** means the patch deliberately produces different bits: a different but valid summation order or rounding point (012, 025), a different kernel (014, 020), a different weight representation (033; 029 for the draft only), or the fix of a bug. A patch that only moves work in time counts as "none" unless it changes reduction shapes. At a glance: 011, 019, 022, 032 and 035 are bit-exact; 001, 003 and 031 have no numerics effect (031 stays within the run-to-run variation described next); 012, 014, 020, 025 and 033 change numerics, and 029 changes the draft only. Of the build-time edits, B1 swaps the attention kernel stock vLLM would use on GB10, B2-B5 are expected to be numerically neutral, and T1 changes no numerics.

Two boots of one configuration already differ. Triton autotuning changes bits between boots, and the indexer's top-k orders its pools through shared-memory atomics, so greedy outputs diverge after a median of 29 tokens even between two CUDA-graph captures on one boot. A change is therefore judged against that floor with a decode-KL protocol. 24 corpus rows (1,024-token prompts, 512 generated tokens, greedy, MTP on) are generated on a reference boot and on the candidate. The tooling reports the mean KL divergence between the two next-token distributions ("KL20" below), the mean absolute difference of the chosen token's logprob (|Δlogprob|) and the median common-prefix length. Two boots of identical configurations give KL20 0.0064, |Δlogprob| 0.0202 and a median prefix of 42 (the "cross-boot floor"); at or below it a change cannot be told from rebooting. Quality checks run on top: logit fidelity on a fixed corpus, 24 tool-call JSON checks, needle retrieval at 16k/32k/48k, GSM8K (50 problems), HumanEval+ (20 problems) and MTP acceptance per draft position.

Numerics statements below are relative to v0.32.0's own code path, and the decode-KL figures were measured on the previous base. Three differences between the two bases are not patch effects but also move numerics: v0.32.0 runs FlashKDA for KDA prefill (section 5); FlashInfer 0.7.0.post1 replaces the 0.6.18 development build (its MLA kernel differs by one clamp that matters only for fully masked rows); and v0.32.0's mHC pre-norm kernels square their input in fp32, where the previous base squared in bf16.

### 1.5 How to read the measurements

All measurements use eight nodes with the GPU clock capped at 2,200 MHz. Each per-patch figure was measured against the configuration it was added to, so the figures do not add up. The result for v0.32.0 as a whole is the table at the top of the [README](README.md#results-at-a-glance).

- **Decode, one user.** Two paired arms, with the same prompts and seeds in every configuration: "chat" (12 requests of 400 tokens) and "agent contexts" (16 recorded agent turns with 7-49k-token contexts, 256 tokens, 2 repetitions). Brackets are 95 % confidence intervals of the paired difference; "n.s." means the interval includes zero.
- **Cold prefill.** One request at a time with a fresh cache salt (no prefix hit), best of two, after a warm-up (the first long prefill after a boot runs 4-7 % slow). Prompt sizes (8k, 32k, ...) are approximate token counts.

### 1.6 If you change the image or a patch

Because the pins name exact files, a different vLLM image makes the affected patches refuse to start. That is intended. Re-validate each affected patch against the new source (its CPU checks on the new files, then its boot self-test) before you update its hashes. A new patch takes the next free number, is inert unless its own variable is set, pins its targets, requires every anchor to match exactly once, is idempotent, and ends with a verification step that exits non-zero on failure. Files edited by more than one change (paths under `vllm/`):

| File | Edited by, in order |
|---|---|
| `platforms/cuda.py` | B1, B2 |
| `v1/attention/backends/mla/flashinfer_mla_sparse_sm90.py` | B1, then 020 |
| `models/glm5next/nvidia/sparse_indexer.py` | B3, then 035 |
| `model_executor/kernels/mhc/tilelang_kernels.py` | 011, 019 |
| `model_executor/kernels/mhc/tilelang.py` | 019, 022 |
| `models/glm5next/common/model.py` | 025, 032, 033 |

Every other target has a single editor. 020 and 035 depend on the bake: 020 is inert without B1, and 035 refuses the unbaked files (it pins B3's and B4's results). 031 accepts either form of `sparse_indexer.py`.

## 3. The changes, one by one

### 3.1 Build-time bake

`image/Dockerfile` starts from the base image and runs `image/glm53_sm121_v032.py`, which edits vLLM and FlashInfer source files in site-packages and installs one data file. It needs no network, pip or GPU. The script plans every edit first and writes nothing unless all of them succeed: every anchor must match exactly once, every file's sha256 must equal its pin, and every edited Python file must compile. A re-run is a no-op, and the build then runs `image/verify_bake.py` on the result. Skip a group with `--build-arg BAKE_ARGS="--skip <group>"` (groups: `attn`, `pdl`, `topk_neg1`, `kpool_pid`, `moe`). How to build and check the image is in [image/IMAGE.md](image/IMAGE.md).

The Dockerfile also sets the serving defaults the recipe relies on: `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`, `VLLM_ENGINE_READY_TIMEOUT_S=3600` (a cold eight-node boot with JIT builds takes longer than the 600 s default), `TORCH_CUDA_ARCH_LIST=12.1a`, `FLASHINFER_CUDA_ARCH_LIST=12.1a`, and the telemetry opt-outs `VLLM_NO_USAGE_STATS=1` and `DO_NOT_TRACK=1`.

Credits, one line each:

- The original SM121 bake is MiaAI-Lab's (`GLM-5.3-Flash-NVFP4-Dual-DGX-Spark`, MIT; notice in `image/LICENSES/`).
- The FlashInfer 0.7.0.post1 retargets (FP8 gate, tile cap, separate JIT name) and the `major != 12` form of B2 follow SpaceshipCreative/glm-5.3-flash-spark (Apache-2.0, MIT parts from MiaAI-Lab).
- The idea of running FA2 with FP8 KV on GB10 also circulates in kindlingai/glm-5.3-flash-gx10 and knapcio/GLM-5.3-Flash-4x-DGX-Spark-TP4.

#### B1 — SM90 sparse-MLA backend on SM12x through FlashInfer FA2

- **Problem.** On a capability-12 GPU, stock vLLM v0.32 serves GLM-5.3-Flash with the `FLASHINFER_MLA_SPARSE_SM120` backend. It stores the MLA KV cache as `fp8_ds_mla` (656 B per token per layer instead of 512 B for plain `fp8_e4m3`) and has no dense-MHA prefill for short prompts. The backend the recipe was tuned on, `FLASHINFER_MLA_SPARSE_SM90`, is refused on capability 12. FlashInfer's FA2 kernel cannot run FP8 KV on GB10 as built either: FlashInfer picks a 16-wide KV tile for GB10's shared memory, then forces 32 for FP8, which needs 117,312 B against GB10's 101,376 B per block, so `cudaFuncSetAttribute` fails with "invalid argument". Tile 16 needs 91,680 B.
- **Change.** Six anchored edits. In vLLM: `platforms/cuda.py` lists the SM90 backend ahead of SM120 for capability 12 (so no `--attention-backend` flag is needed); `flashinfer_mla_sparse_sm90.py` accepts capability 12 and builds FlashInfer's wrapper with `backend="fa2"` off Hopper (FA3 needs wgmma). In FlashInfer: the plan-time validator accepts FP8 KV for MLA on SM12x with fa2 (the check is a test-coverage limit, not a kernel limit); `mla.cuh` caps the FP8 KV tile at 32 instead of forcing it, so GB10 gets tile 16; the patched module gets its own JIT name suffix (`_fp8tilecap`), so a stock or prebuilt FlashInfer module can never be picked up for it.
- **Switch.** None at run time; build group `attn` (all or nothing). Check on every rank: `Using FLASHINFER_MLA_SPARSE_SM90 attention backend out of potential backends: ['FLASHINFER_MLA_SPARSE_SM90', 'FLASHINFER_MLA_SPARSE_SM120'].` and no `Using fp8_ds_mla KV cache format` line. FlashInfer JIT-builds the module on first use on each node, which takes several minutes the first time.
- **Numerics.** Not comparable with stock v0.32 (different kernel and cache layout). Against the previous base's kernel the arithmetic is the same: the 16-wide tile fixes the online-softmax tile width, as before, and the FlashInfer upgrade changes only the clamp mentioned in section 1.4.
- **Effect.** Enabler; no isolated measurement.
- **Upstream.** Not upstream. v0.32.0 allows the SM90 backend on capability 9 only, lists `[TRITON_MLA, FLASHINFER_MLA_SPARSE_SM120]` for capability 12, and FlashInfer's FP8 MLA path checks for SM90. Upstream's own SM12x route for this model (`FLASHINFER_MLA_SPARSE_SM120`, #55277, v0.31.0) uses the packed layout above; we found no published GB10 numbers for it with this model.

#### B2 — PDL off on SM12x

- **Problem.** Programmatic dependent launch lets the next kernel start before the previous one finishes. vLLM enables it on every GPU of capability 9 or higher. On GB10, community reports describe races in the KDA recurrent-state kernels and the mHC kernels: a boot that produces NaNs or not, depending on launch timing.
- **Change.** `is_arch_support_pdl()` in `platforms/cuda.py` returns `major >= 9 and major != 12`. Every PDL user (KDA state kernels, fused norm-gate, QK RMSNorm, the mHC TileLang kernels, which cache the flag at import) sits behind that one function. Other capabilities are unchanged.
- **Switch.** Build group `pdl`. Check: `python3 -c "from vllm.platforms import current_platform as p; print(p.is_arch_support_pdl())"` prints `False` on a GB10 node.
- **Numerics.** Launch scheduling only. Bit-identical wherever PDL does not race; it removes a source of nondeterministic corruption and costs the launch overlap on those kernels.
- **Effect.** Not measured separately; the previous base also ran with PDL off.
- **Upstream.** Still on for capability 9 and up; we found no upstream PR to change it.

#### B3 — Pool top-k buffers start at -1

- **Problem.** The indexer allocates its pool top-k buffers with `torch.empty`. A slot the top-k kernel leaves unwritten would hold garbage that later expands to a bogus token index, which is silent corruption (community-reported).
- **Change.** Both allocations in `models/glm5next/nvidia/sparse_indexer.py` (prefill and decode) use `torch.full(..., -1)`.
- **Switch.** Build group `topk_neg1`.
- **Numerics.** Bit-exact whenever every slot is written, which is expected on v0.32.
- **Effect.** One extra memset per indexer layer per step (12 layers including the MTP layer): tens of microseconds per decode step and about 1 ms per 8,192-token prefill chunk by estimate, not measured.
- **Upstream.** v0.32 kernels write -1 into every slot past a short row themselves, and the dispatcher documents that contract, so this edit is expected to be a no-op. It stays as defence in depth because the failure mode is silent.

#### B4 — Pool ids must be below `pool_len`

- **Problem.** `_expand_pools_and_append_tail_kernel` (`models/glm5next/nvidia/ops/kpool_compress.py`) keeps every pool id that is `>= 0`. Only `seq_len // 4` pools are complete; an id at or past that (a stale slot, or a selection that touches the incomplete trailing pool) expands to positions beyond the sequence or repeats the tail the kernel appends right after.
- **Change.** The kernel keeps only `0 <= pid < pool_len`; other ids become -1 (excluded).
- **Switch.** Build group `kpool_pid`.
- **Numerics.** Bit-exact for valid ids. Invalid ids are excluded instead of attending to tokens that do not exist or are duplicated.
- **Effect.** A correctness guard, not a speed change.
- **Upstream.** Not in v0.32.0 or in main at the time of writing.

#### B5 — Tuned MoE table for E=288 on GB10

- **Problem.** Triton fused-MoE takes its tile shapes from a per-GPU table. vLLM ships GB10 tables for E=256 and E=512 only; GLM-5.3-Flash has 288 routed experts (N=256 per rank at TP=8), so without a table vLLM logs "Using default MoE config. Performance might be sub-optimal".
- **Change.** Installs `E=288,N=256,device_name=NVIDIA_GB10,dtype=fp8_w8a8,block_shape=[128,128].json` (20 batch-size entries, 1 to 8,192) into `model_executor/layers/fused_moe/configs/`, where vLLM looks without any environment variable.
- **Switch.** Build group `moe`. Check: `Using configuration from .../E=288,N=256,device_name=NVIDIA_GB10,...json for MoE layer.` and no "Using default MoE config" warning.
- **Numerics.** Tile sizes (`BLOCK_SIZE_M/N`), warps and stages only. Every entry keeps `BLOCK_SIZE_K` = 128, the block-quantization group, so the K loop and the scale order are vLLM's. An earlier microbenchmark found identical outputs.
- **Effect (measured on the previous base, where the table was an option and not enabled).** Chat decode +1.0 % and +2.1 %, agent contexts +0.6 % and -0.1 %, cold prefill -1 to -1.5 %. Marginal; the table is in the image because it costs nothing in numerics. Build with `--skip moe` for a table-free comparison.
- **Upstream.** Upstream has GB10 tables for E=256 and E=512 (#52502); nothing for E=288.

### 3.2 Runtime patches

Applied by `patches/entrypoint.sh` in numeric order. "Boot line" names the runtime line to look for.

#### 001 — IPC spin-wait grace (`001-gb10-spin-wait.sh`)

- **Problem.** vLLM's cross-process wait (`shm_broadcast.SpinCondition`) spins on a core for `busy_loop_s` (default 1 s) before it sleeps. Decode messages arrive faster than that, so the sleep path never engages and three to four performance cores sit at full clock. On GB10 the CPU-cluster sensor, not the GPU, is the hottest thermal zone.
- **Change.** One value in `distributed/device_communicators/shm_broadcast.py`: `busy_loop_s: float = 1` becomes `0.002` (a 2 ms grace, then sleep). A wait policy, not a computation; TP >= 2 only.
- **Switch.** None; always applied. The script accepts only the original file and its own result. Boot line: `[OK] busy_loop_s = 0.002 — IPC wait sleeps after 2ms instead of spinning 1s.`
- **Numerics.** None.
- **Effect (measured on the previous base).** With CUDA graphs on, the engine-core scheduler thread's CPU use fell from 40 % to 9 %. Alone, in eager mode, it did not remove the thermal spikes, because two genuinely busy host threads shared one core cluster; the worker main thread kept spinning until 003.
- **Upstream.** No knob: `busy_loop_s` is unchanged up to main, and the proposal to make it configurable (#52814) is not merged. Origin: the DSpark recipe by MiaAI-Lab and Anemll (their issue #79).

#### 003 — CUDA blocking sync for the worker processes (`003-gb10-blocking-sync.sh`)

- **Problem.** When a worker waits for the GPU, CUDA's default scheduling spins the calling thread, so one core per rank sits near 100 % for most of every step and the node heats up. Turning async scheduling off removes the spin but slows decode (median inter-token latency 37 vs 30 ms) and adds IPC stalls of about 5 s (measured on the previous base).
- **Change.** Installs `vllm/_gb10_blocking_sync.py` and adds two calls in `Worker.init_device` (`v1/worker/gpu_worker.py`) around `set_device_index`: before the primary CUDA context exists it requests blocking-sync scheduling, afterwards it verifies the flag. Waiting threads sleep until the GPU signals; async scheduling stays on.
- **Switch.** `VLLM_GB10_BLOCKING_SYNC=1` on every rank. If the variable is set but the flag cannot be verified, the worker raises at init. Boot line: `[gb10-blocking-sync] device N: CUDA context schedule = BLOCKING_SYNC ...`.
- **Numerics.** None (a CUDA context scheduling flag).
- **Effect (measured on the previous base).** Worker main-thread CPU 96-100 % -> 8-20 %, thermal-watchdog aborts gone, hottest node peak 80.6 vs 87.0 °C; the price is about 2 ms of wake latency per step. v0.32 plans the sparse-MLA step from a host upper bound (#58684), so most of the device-to-host waits this patch was written for are gone; its benefit on v0.32 has not been re-measured separately.
- **Upstream.** No equivalent (main has no handling of the blocking-sync schedule flag).

#### 011 — mHC pre-norm: block_m=2 kernel from 128 tokens (`011-mhc-prenorm-bm2-threshold.sh`)

- **Problem.** The mHC pre-norm GEMM uses its block_m=2 TileLang kernel only from 1,024 tokens. For 128 <= T < 1,024 (agent appends, chat prompts, tail chunks of a prefill) it runs the generic per-token kernel, whose thread blocks each re-read a 786 KB fp32 weight slice from L2: 33 GB/s on GB10, 90 calls per forward.
- **Change.** Four anchored edits in `model_executor/kernels/mhc/tilelang_kernels.py` make the threshold in `HcPrenormGemmTileLangKernel.dispatch()` a module constant read from the environment at import, and make the JIT warm-up buckets and the block_m warm-up tensor follow it. T < 128 keeps its small-T kernel; calls of up to 32 tokens (decode) take upstream's fused kernel and never reach this path. A larger block_m is slower on GB10 (register pressure), so only the threshold moves.
- **Switch.** `VLLM_GB10_MHC_BM2_MIN_T=128` (an integer >= 128; unset keeps 1,024). Set it on every rank.
- **Numerics.** Bit-exact: both kernels accumulate each token's row in the same order with the same reductions (checked on the kernel IR, and bitwise on the GPU on the previous base at every T tested).
- **Effect (measured on the previous base).** Per call at T = 128 / 256 / 512: 132 / 252 / 509 -> 79 / 120 / 240 µs. Cold prefills of 256-1,000 tokens took 4.3-7.4 % less time; 100 and 1,024 tokens were unchanged.
- **Upstream.** The rule is still `num_tokens >= 1024` upstream; the kernels became JIT classes in #50178 (v0.30.0).

#### 012 — One-shot all-reduce for small tensor-parallel messages (`012-gb10-oneshot-allreduce.sh`)

- **Problem.** Decode all-reduces (8-64 KiB, about 96 per step) are latency-bound. NCCL's tree takes about six sequential host-staged hops over 100 GbE because GB10 has no GPUDirect RDMA. A grouped send/recv to all peers plus a local sum is one network step.
- **Change.** Installs `vllm/_gb10_oneshot_ar.py` and makes two anchored edits in `distributed/device_communicators/cuda_communicator.py`. `__init__` creates the helper for the TP group; its constructor runs a collective, self-checking warm-up. `all_reduce` hands contiguous bf16 tensors of at most `MAX_BYTES` to it as its first statement: the vector goes to all seven peers in one grouped send/recv, is summed locally in fp32 in rank order and rounded once to bf16, giving identical bits on every rank. Everything else (larger messages, other dtypes) stays on NCCL.
- **Switch.** `VLLM_GB10_ONESHOT_AR=1` on every rank (`_MAX_BYTES`: a positive even number, default 65536). v0.32 turned `all_reduce` into a dispatch chain with FlashInfer's all-reduce on by default; with `VLLM_ALLREDUCE_USE_FLASHINFER=0` and `--disable-custom-all-reduce` the rest of the chain ends in NCCL as before (section 5.5), and the script warns if the patch is on and that variable is not `0`. A wrong sum in the warm-up stops the boot. Boot lines: `Using ['PYNCCL'] all-reduce backends (in dispatch order) for group 'tp:0'` and `[patch-012] one-shot all-reduce ACTIVE for group tp:0 (world 8, bf16 <= 65536 bytes; larger messages use NCCL)`.
- **Numerics.** Changes. It differs from NCCL's per-hop bf16 additions, so greedy outputs are not bit-equal to a stock all-reduce. It is closer to the exact sum: the maximum error is 2-10 times smaller than NCCL's tree at the sizes tested (0.078 vs 0.205 at n = 4,096). On the previous base the decode-KL of the patched run against its parent was indistinguishable from the cross-boot floor (KL20 0.0034-0.0037, |Δlogprob| 0.0101-0.0107).
- **Effect (measured on the previous base).** Graph-replay all-reduce on 8 nodes at 8 / 16 / 32 / 64 KiB: tree 79 / 98 / 121 / 124 µs vs one-shot 52 / 49 / 64 / 86 µs. Decode, one user, paired against the parent: chat +11.4 % [+10.4, +15.5], agent contexts +12.0 % [+5.8, +14.9], acceptance length unchanged (2.64 vs 2.66). Four-user chat +18 %.
- **Upstream.** Nothing upstream for multi-node RoCE: FlashInfer all-reduce, the PCIe-IPC route and symmetric memory are single-node.

#### 014 — Skinny kernels for the narrow indexer projections (`014-gb10-skinny-indexer.sh`)

- **Problem.** Each sparse-attention layer's indexer projects the hidden states [M, 4096] through three narrow matrices: `wk_weights_proj` [160, 4096] (bf16), an fp32 head gate (`torch.mm(x.float(), W[4096, 32])`) and the kpool gate [128, 4096] (bf16). - **Change.** Installs `vllm/_gb10_skinny_idx.py` and makes three anchored edits in `models/glm5next/common/attention.py` (import, `Indexer.forward`, kpool-gate call). For 1 <= M <= 16 with bf16, contiguous, 16-byte-aligned input: at M <= 3 a CuTe skinny GEMM plus a dot-product kernel (both ship in vLLM's tree for other callers); at M 4-8 cuBLAS plus the dot-product head gate; at M 9-16 cuBLAS plus a Triton split-K head gate. Prefill is untouched.
- **Switch.** `VLLM_GB10_SKINNY_IDX=1`. Boot lines: `[patch-014] skinny indexer ACTIVE ...` with the per-M route table, then one `self-test OK` per indexer (11 target layers plus the MTP layer).
- **Safety.** On its first eager call (the profile run) each indexer compiles every variant for M = 1...16 and self-tests against the original path at every M; a failure raises, and so does a first call inside a CUDA-graph capture.
- **Numerics.** Changes in the last bit. The head gate sums the same fp32 products in a different order (error against exact 7.0e-8 vs 6.6e-8). `k` and the gate outputs are within 1 bf16 ulp of cuBLAS's on at most 0.78 % of elements at M <= 3 and bit-identical at M >= 4. Deterministic and identical on all ranks. Decode-KL on the previous base: KL20 0.0035, |Δlogprob| 0.0124, at the floor.
- **Effect (measured on the previous base).** Per layer at M = 1 / 3 / 8 / 16: 32.0 / 129.9 / 92.4 / 91.1 -> 12.6 / 12.9 / 22.2 / 23.1 µs, about 1.6 -> 0.2 ms per decode step. Decode: chat +6.5 % [+2.2, +8.7], agent contexts +1.9 % [-1.3, +3.9], n.s.
- **Upstream.** No upstream change; the indexer still has the same three projections.

#### 019 — Fused mHC decode kernel on bf16 weights (`019-gb10-mhc-fn-bf16.sh`)

- **Problem.** Every decode step runs 89 fused mHC post + pre-norm calls for up to 32 tokens, each one TileLang kernel whose weight operand is the fp32 parameter `fn` [24, 16384] (1.5 MiB per call). The checkpoint stores all 90 `hc_*_fn` tensors as bf16 (no subnormals, zeros or non-finite values); vLLM widens them to fp32, so half of every fp32 word is zero.
- **Change.** Installs `vllm/_gb10_mhc_fn_bf16.py`: a kernel class (`MhcFusedBf16wTileLangKernel`) that is vLLM's fused kernel with only the weight operand declared bf16, registered in vLLM's JIT warm-up registry, plus a cache of bf16 copies. Four anchored edits in `model_executor/kernels/mhc/tilelang.py` and `tilelang_kernels.py` make the small-M fused launch use the cached copy (made on the first eager call of each weight) and register the variant for warm-up; otherwise the original fp32 line runs. Larger M (prefill, where 011 and 022 act) and layer 0's pre-op are untouched. Cost: +66.75 MiB per rank (89 copies of 768 KiB).
- **Switch.** `VLLM_GB10_MHC_FN_BF16=1`. Boot lines: `[patch-019] mHC fn bf16 ACTIVE ...` and, at the first capture, `[patch-019] 89 bf16 hc_*_fn copies (66.75 MiB) ... first seen inside a capture: 0`.
- **Safety.** Each fp32 element has zero low 16 bits, so the conversion is exact; every weight is checked bitwise and the process raises otherwise. Boot self-test: both kernels at M = 1, 7, 8, 15, 16, 24, 32 must agree bitwise, through the raw JIT functions and through the production classes, or the process raises. A weight first seen inside a CUDA-graph capture keeps the fp32 kernel in that graph (with a warning).
- **Numerics.** Bit-exact. TileLang promotes the bf16 operand to fp32 exactly as it already does for the kernel's other operands; an AST comparison and a comparison of the generated IR show that only three statements differ.
- **Effect (measured on the previous base).** The 89 fused calls take 1.149 -> 0.938 ms per forward at M = 3 (-0.21 ms) and 2.388 -> 1.886 ms at M = 16: about 0.4-0.5 % of a batch-1 step, below what the paired arms resolve (chat -1.0 % [-5.7, +0.8], agent contexts -0.5 % [-3.1, +4.0]: no regression). v0.32's fused kernel covers up to 32 tokens with new tile configurations, so the gain there has not been re-measured.
- **Upstream.** Upstream's fused kernel still takes the fp32 weight. Origin: the kernel is a copy of vLLM's `mhc_fused_tilelang` (Apache-2.0) with one annotation changed; the bf16-weights idea comes from kindlingai/glm-5.3-flash-gx10 (no code copied).

#### 020 — Triton prefill kernel for sparse MLA (`020-gb10-sparse-mla-triton-prefill.sh`)

- **Problem.** On GB10 every row of a sparse-MLA step runs the FlashInfer FA2 wrapper. Masked sparse MHA needs SM100, and the dense-MHA prefill fires only while the prefill context is at most `index_topk` = 2,048 tokens, so longer prompts prefill through the same wrapper that serves decode.
- **Change.** Installs `vllm/_gb10_sparse_mla_prefill.py` and makes five anchored edits in `v1/attention/backends/mla/flashinfer_mla_sparse_sm90.py` (the file B1 also edits). Prefill rows go to a Triton fused sparse-attention kernel: it reads the E4M3 latent cache directly, dequantises K and V with `k_scale`, scales q exactly by a per-head power of two against fp16 overflow, accumulates in fp32 and merges at most two splits in a fixed order. Decode rows keep FA2, planned for the decode rows only. Pure-decode steps run vLLM's own call sequence, bit for bit, and stay CUDA-graph safe. The kernel requires an fp8 KV cache and a NoPE layout with 512-wide latents; a start-up check refuses anything else.
- **Switch.** `VLLM_GB10_SPARSE_MLA_TRITON_PREFILL=1` on every rank. With the gate set, an import failure raises at backend import; the start-up check also runs an on-device self-test that compiles both kernel variants. Without B1 the SM90 backend cannot be selected on GB10, and the script then prints `[state] patch 020 inert` and touches nothing. Boot lines: `[patch-020] Triton sparse-MLA prefill self-test OK ...` and one `[patch-020] ACTIVE ...` per rank.
- **Numerics.** Changes for prefill rows, whose KV feeds later decode. Against an fp64 reference of the dequantised attention (measured on the previous base): Triton mean relative error 1.28e-3 (p99 3.5e-3), FA2 on the same rows 2.24e-3 (p99 1.0e-2), Triton vs FA2 1.7e-3. Decode-KL at the floor (KL20 0.0061, |Δlogprob| 0.0147). Decode rows in a mixed step are planned for fewer rows, so FA2's splits differ and results can move by about one ulp (not measured).
- **Effect (measured on the previous base).** Cold prefill: 1k +3.7 %, 2k +7.8 %, 4k +13.2 %, 8k +15.9 %, 16k +17.0 %, 32k +16.5 % (2,053 -> 2,391 tok/s), 64k +17.8 %; decode unchanged. That run also had the sync-free builder that upstream now provides (#58684), and the Triton kernel's own share was not measured separately.
- **Upstream.** No NVIDIA Triton sparse-MLA prefill upstream (only a ROCm one), and masked sparse MHA stays SM100-only. The other half of the old patch, the sync-free builder, is upstream (section 4). Origin: a port of vLLM's ROCm AITER sparse-MLA prefill kernel (Apache-2.0) with the split-KV idea of vLLM #47629.

#### 022 — mHC pre-norm row split across ranks in prefill (`022-gb10-mhc-prefill-rowsplit.sh`)

- **Problem.** mHC is replicated under TP: every rank runs the pre-norm GEMM on the full residual [T, 16384] for every mHC block (90 calls per forward). In prefill it is the slowest mHC kernel: 90 x 1.88 ms = 169 ms per 3,840-token chunk on the previous base, roughly 10 % of a chunk.
- **Change.** Installs `vllm/_gb10_mhc_prs.py` and makes two anchored edits in `model_executor/kernels/mhc/tilelang.py` (gate and import; a hook in the TileLang branch of `_hc_prenorm_gemm_outputs`). For T >= `MIN_T`, outside a CUDA-graph capture, rank r runs the same kernel on rows [r·S, min((r+1)·S, T)) with S = 2·ceil(ceil(T/2)/8). Shard starts are even, so every shard block is a block of the full call. One NCCL all-gather of the per-row outputs rebuilds the result on every rank. Decode is untouched.
- **Switch.** `VLLM_GB10_MHC_PRS=1` on every rank; `_MIN_T` default 1,024 (accepted 256 to 1,048,576). It needs `VLLM_USE_DEEP_GEMM=0`: the hook sits in the TileLang branch, and with DeepGEMM on, vLLM takes DeepGEMM's `tf32_hc_prenorm_gemm` instead (sm_121 is DeepGEMM-capable) and the patch would be silently inert, so the script warns. Boot line: `[patch-022] mHC prefill row-split ACTIVE (rank r/8, T >= 1024, ...)`.
- **Safety.** Collective boot self-test on the 8,192-token profile run: the split result must equal the unsplit kernel bitwise on every rank (live call plus synthetic inputs at several T), be repeat-stable and fully written, with a matching rank fingerprint; TP must be 8 and PP 1. Any failure raises on every rank.
- **Numerics.** Bit-exact. Each output row depends only on its own input row and the weight (per-thread fp32 accumulators in a fixed order, no arithmetic reads T or another row), and the gather is a copy.
- **Effect (measured on the previous base).** Split plus gather 0.757 ms vs 3.817 ms unsplit per call at T = 8,192. Cold prefill against the same configuration without it: 1k +6.7 %, 4k +7.5 %, 16k +8.7 %, 32k +8.5 % (2,617 vs 2,413 tok/s), 64k +8.9 %. With 025 on, as served, every eligible prefill is a 025 region and 022 does not split while serving (it runs once, inside 025's boot self-test); 022 is the prefill path when 025 is off. Decode all-reduces keep taking 012.
- **Upstream.** No equivalent.

#### 025 — Sequence-parallel mHC in prefill (`025-gb10-mhc-prefill-sp.sh`)

- **Problem.** At TP=8 every mHC block and the 91 all-reduces per forward are replicated on all eight ranks. On the previous base mHC took about 357 ms, around 22 % of a 3,840-token prefill chunk.
- **Change.** Installs `vllm/_gb10_prefill_sp.py` and makes four anchored edits in `models/glm5next/common/model.py`: a module gate; a dispatch of eligible forwards to `sp_layer_forward` at the start of `Glm5NextDecoderLayer.forward`; the sharding of the residual stream around the layer loop of `Glm5NextModel.forward`; and the gather before the final norm. In an eligible prefill each rank keeps T/8 rows and runs every mHC block on them, and the per-block attention/MoE all-reduce becomes a reduce-scatter (with an all-gather before the next input): the same bytes, with the mHC work divided by eight. Eligible means T >= `MIN_T`, eager, outside a CUDA-graph capture, not micro-batched and without EAGLE-3 aux taps. Decode and short prefills never shard.
- **Switch.** `VLLM_GB10_MHC_SP=1` and `VLLM_USE_DEEP_GEMM=0` on every rank; `_MIN_T` (default 1,024, floor 1,024); `_RS` (`nccl` default, or `canonical`). It composes with 022 (see 022). Boot line: `[patch-025] mHC prefill sequence-parallel ACTIVE (rank r/8, mode=sp, rs=nccl, T >= 1024, ...)`.
- **Safety.** Hang-free boot self-test: every collective is issued on every rank with a pre-checked shape, and verdicts travel over gloo behind a bounded 600 s barrier; 43 cases, including the live weights of layer 0 (KDA + dense) and layer 3 (MLA + MoE). - **Numerics.** Changes the prefill reduction order. NCCL's ring reduce-scatter does not reproduce the ring all-reduce's element order (about 52 % of elements differ bitwise; both are valid sums). All ranks still hold identical outputs: each row is computed on one rank and the final gather is a copy. `_RS=canonical` (a fixed rank-order fp32 sum on 012's transport) makes sp bitwise equal to its replicated reference; the recipe uses `nccl`. Decode-KL against the parent on the previous base: KL20 0.0043, |Δlogprob| 0.0134, at the floor.
- **Effect (measured on the previous base).** Cold prefill, one user, with vs without: 8k 3,107 tok/s (+13.2 %), 32k 3,281 (+15.3 %), 64k 3,327 (+15.7 %), 128k 3,342 (+15.6 %), 258k 3,322 (+15.5 %), 512k 3,269 (+15.5 %); 512k TTFT 181.0 -> 156.6 s. Decode essentially unchanged; prompts below 1,024 tokens unchanged.

#### 031 — Depth gate for the sharded indexer prefill (`031-gb10-idx-shard-gate.sh`)

- **Problem.** The indexer (11 target layers plus the MTP layer; 32 heads x 128, `index_kpool` 4, top-512 pools) is replicated under TP: in prefill every rank scores every query row against all pooled keys. The cost grows with depth: on the previous base the fit `t/N = 0.372 ms + 1.71e-7 ms x N` (64k to 1M within 1 %) put it at about 32 % of a 1M-token prefill. v0.32.0 can shard those rows over the TP group (#54951: each rank scores a contiguous share, balanced by indexer work, then the group exchanges the selected token ids), but only when one step holds at least 16,384 x TP rows. That is 131,072 rows at TP=8, which never happens at 8,192 batched tokens.
- **Change.** One file, four anchored edits in `v1/attention/backends/mla/indexer.py`. The row-count test in `balanced_prefill_row_shard` becomes a gate: shard when the step has at least `MIN_ROWS` indexed rows and the deepest prefill request has at least `MIN_CTX` tokens of context. With the gate unset, vLLM's own decision runs unchanged. The patch adds one boot line per rank and logs the first sharded step; it installs no module and adds nothing to the forward path except upstream's own sharded branch. Decode, short prefill (context <= 2,048), graph paths and KV writes are untouched.
- **Switch.** `VLLM_GB10_IDX_SHARD=1` on every rank (a rank that disagrees would skip a collective the others enter and hang until the execute timeout). `_MIN_CTX` (4,096 to 4,194,304, default 32,768) and `_MIN_ROWS` (64 to 8,192, default 256) can be tuned without re-pinning; a bad value raises at import. There is no boot self-test: the sharded branch is upstream's code, and the gate is a pure function of scheduler metadata that is the same on every rank. Boot lines: `[patch-031] indexer prefill row-shard ACTIVE (rank r/8; context >= 32768 tokens and >= 256 rows, ...)`, or `... INACTIVE (rank r/8): <why>` when upstream's own support check says no (full CUDA-graph mixed mode, context parallelism, symmetric-memory NCCL, batch-invariant mode, ...); and `first sharded indexer prefill step: N rows -> ...`.
- **Numerics.** Gate unset: bit-for-bit vLLM. Gate on: per row the same kernels run on the same data, and a row's logits do not depend on which rank scores it, so the pool sets are identical. The order of the pools, and the members on exact ties at the 512th value, come from the rank that scored the row; that is the run-to-run class the replicated top-k kernel already has. Upstream's split is not aligned to the 16-row groups the previous patch used (that patch verified bitwise at boot), and there is no boot check here.
- **Effect (measured on the previous base, with the previous patch's own sharding code and exchange).** Cold TTFT, one user, 1M window, against the same stack without it: 128k 49.7 vs 51.3 s (+3.4 %), 258k 98.2 vs 106.5 s (+8.3 %), 512k 201.9 vs 241.9 s (+19.8 %), 1M 413.1 vs 572.4 s (+38.6 %, 2,518 tok/s); 64k unchanged. Upstream's exchange moves four times as many bytes per call (see 035). We expect that to push the depth at which sharding pays upward; the recipe keeps the default `MIN_CTX`, the value measured on the previous base.
- **Upstream.** Partly upstream: #54951 (v0.32.0) provides the sharding with a row-count gate only; #61647 (main) makes that gate configurable (`attention_config.indexer_tp_shard_min_rows`, default 65,536 total rows) and still has no depth criterion. Idea credit: vLLM PR #54951 (Apache-2.0).

#### 032 — Replicated input embedding (`032-gb10-repl-embed.sh`)

- **Problem.** Each decode step replays three CUDA graphs: target, MTP draft prefill, MTP draft decode. The first NCCL kernel of each replay waits 0.5-0.9 ms on NCCL's per-plan host-callback node, a GPU -> CPU -> GPU round trip (511 / 915 / 621 µs on the critical path, plus about 0.54 ms of slower first floors per step). In all three replays that first op is the vocabulary-parallel embedding all-reduce, 5-14 µs into the replay, so nothing hides the wait.
- **Change.** Installs `vllm/_gb10_repl_embed.py` and makes two anchored edits in `models/glm5next/common/model.py`: a gated import, and in `Glm5NextModel.__init__` the input embedding becomes `ReplicatedEmbedding`, vLLM's `VocabParallelEmbedding` built with `disable_tp=True`. That is the full table [154,880 x 4,096] on every rank, looked up with vLLM's own fused kernel and no all-reduce. The first NCCL op of each replay is now the first layer's (244 / 742 / 742 µs of compute later), so the round trip runs under compute. The MTP drafter shares the target's `embed_tokens`; `lm_head` is untouched. Outside the validated envelope (TP 8, PP 1, no LoRA, untied embeddings, vocabulary a multiple of 64 and of TP, bf16) the stock class is used. Cost: +1.03 GiB per rank.
- **Switch.** `VLLM_GB10_REPL_EMBED=1` on every rank; incompatible with 029's `eh` part. Boot line: `[patch-032] replicated input embedding ACTIVE (rank r/8; ...)`.
- **Safety.** Boot self-test (every rank, after all weights, fail closed): a table scan; a gloo exchange with a content digest (a checkpoint copy that differs between nodes is caught); the lookup against the stock computation (the real vocab-parallel lookup plus all-reduce) bitwise for all 154,880 ids; probes of 1-8, 16, 48 and 3,840 tokens; a replayed CUDA graph. Active only if every rank passed; otherwise every rank restores the stock layer.
- **Numerics.** Bit-exact. For an in-range id the stock path all-reduces the owner's row with seven rows of +0.0. NCCL's bf16 sum and 012's one-shot both return x exactly for every finite non-zero x and +0.0 for -0.0, so the stock output is the table row with -0.0 turned into +0.0. At boot the replicated table's -0.0 elements are rewritten as +0.0, and the self-test compares bitwise. Decode-KL on the previous base: KL20 0.0059, |Δlogprob| 0.0126 (the floor).
- **Effect (measured on the previous base).** Decode paired against the parent: chat +5.1 % [+3.1, +5.7] and +4.6 % [+3.5, +5.9] (12 of 12 requests faster each), agent contexts +3.7 % [+0.5, +6.3] and +3.7 % [+2.3, +7.4]; acceptance unchanged; prefill +0.3 to +0.6 %.
- **Upstream.** No equivalent.

#### 033 — MLA projections as FP8 W8A16 in decode (`033-gb10-mla-w8a16.sh`)

- **Problem.** The 11 MLA layers (3, 7, ..., 43) and the MTP layer (45) store `q_a_proj`, `kv_a_proj_with_mqa`, `q_b_proj` and `o_proj` as block-FP8 (e4m3, 128 x 128 blocks, `weight_scale_inv`), but vLLM dequantises them to BF16 at load. Every decode step streams 39.8 MB of BF16 per MLA layer for weights that exist as 19.9 MB of FP8.
- **Change.** Installs `vllm/_gb10_mla_w8a16.py` and makes three anchored edits in `models/glm5next/common/model.py`. A gated import. In `Glm5NextDecoderLayer.__init__` the `quant_method` of `fused_qkv_a_proj`, `q_b_proj` and `o_proj` becomes a subclass of `UnquantizedLinearMethod` (36 projections per rank, the MTP layer included). And `_try_load_fp8_attn_proj` copies the checkpoint's FP8 shard and block scales before the BF16 dequantisation, so the Marlin copy is built from the checkpoint bytes, not re-quantised. A 2-D bf16 input with 0 < M <= `MAX_M` and no bias runs vLLM's Marlin W8A16 kernel; anything else runs vLLM's BF16 GEMM on the BF16 weight, which stays resident. Graph dispatch keys on token count, so any batch of up to 16 tokens (decode, a short prompt, a short follow-up turn, a tail chunk) takes Marlin; longer prefill chunks and graph sizes 24-48 are unchanged. Memory: +0.23 GiB per rank steady, about +0.45 GiB transient until the self-tests finish.
- **Switch.** `VLLM_GB10_MLA_W8A16=1` on every rank; `_MAX_M` (1-64, default 16: the largest M the boot self-test checks and the largest decode token count here, batch size 8 with 2 tokens per request); `_SPEED_GATE` (`graph`, enforced, by default; `info` only logs). Boot line: `[patch-033] MLA FP8 W8A16 (Marlin) ACTIVE (rank r/8): ...`.
- **Safety.** Per-rank boot self-test, fail closed and hang-free: the captured FP8 equals the served BF16 weight bitwise; on the real weights at M = 1...16, the error against fp32, against the BF16 path and against Marlin's own dequantisation, plus determinism and dispatch fidelity; cross-rank digests; an in-graph speed gate (Marlin <= 0.85 x BF16 per 11-layer sweep at M = 3); a gloo vote. A projection type whose module call does not reach the new method falls back alone; any other failure keeps BF16 on every rank. v0.32's Marlin helpers create their lock buffers lazily per stream, so the patch allocates and passes its own at load time, outside any CUDA-graph capture; because it keeps one lock buffer per projection, it refuses dual-batch overlap, which the recipe does not use.
- **Numerics.** Changes, minimally: the checkpoint's own FP8 values, with the block scale rounded to bf16 (at most 1 bf16 ulp; 22.9 % of elements differ by one ulp), through a different GEMM. Output error against fp32: 0.00346 relative RMS vs 0.00247 for the BF16 path. Decode-KL against the parent on the previous base: KL20 0.0071, |Δlogprob| 0.0123, the cross-boot level; quality checks equal to the parent.
- **Effect (measured on the previous base).** Per layer at M = 3, DRAM-cold inside a CUDA graph: BF16 183.5 µs, Marlin 97.2 µs (0.53 x), 1.18 ms per step in total. End to end, one user, paired over two boots of each configuration: chat +1.7 to +3.6 % (mean +2.7 %), agent contexts +0.8 to +5.8 %; acceptance, prefill and 32k TTFT unchanged. The gain is about 1 ms per step rather than 1.18, because 032 already hides NCCL's host-callback wait under the first layers' compute, which includes the MTP layer's projections. Marlin's end-to-end speed at M = 4-16 (2-8 users) was not measured.
- **Upstream.** No equivalent: vLLM still dequantises these projections to BF16 at load.

#### 035 — Compact pool-id exchange for the sharded indexer prefill (`035-gb10-idx-compact-xchg.sh`)

- **Problem.** On v0.32.0 cold prefill is 6-8 % faster than on the previous base at 8k-32k tokens, but 6.5-7.7 % slower from 128k to 1M (1M-token TTFT 358 s vs 330 s), although 031 engages upstream's TP-sharded indexer prefill (#54951) at depth. After its chunk loop, the GLM-5.3 indexer exchanges the expanded token ids: 2,051 int32 per row (8,204 B: the 2,048 top-k tokens plus `index_kpool` - 1 = 3 tail entries) in one `all_gatherv` (eight NCCL broadcasts), in 12 indexer calls (11 target layers plus the MTP layer) per 7,680-row prefill chunk, about 63 MB per call. The previous base's own patch exchanged the 512 pool ids per row (2,048 B, 4.006 times fewer bytes, about 15.7 MB per call) and let every rank expand all rows locally. Whether the wider exchange explains the whole deficit is not established.
- **Change.** One file, five anchored edits in `models/glm5next/nvidia/sparse_indexer.py` (as B3 leaves it). In a sharded step in the served layout (row shard present, `index_kpool` > 1, positions given), each chunk's pool ids are staged at their global rows instead of being expanded. After the loop, one `all_gatherv` of the 512-wide rows (the same group call as upstream's exchange) is followed by one `expand_pools_and_append_tail` over all rows and one write into the top-k buffer. Decode, short prefill, CUDA-graph paths, the `positions is None` branch and `index_kpool == 1` are never touched.
- **Switch.** `VLLM_GB10_IDX_COMPACT_XCHG=1` on every rank, together with 031's `VLLM_GB10_IDX_SHARD=1` (without it no sharded step happens); `VLLM_GB10_IDX_COMPACT_XCHG_VERIFY` (0-1000, default 3, 0 = off). A rank on the other path would enter a gather of a different width and hang until the execute timeout, so the script refuses typos. Boot lines on rank 0 at the first sharded step: `[patch-035] compact exchange ACTIVE (width 512 instead of 2051)` and `[patch-035] verify k/3: bitwise equal (...)`.
- **Safety.** The compact path declines, with a rank-0 warning `compact exchange declined (<why>): the original exchange runs`, when a host assumption fails: step tokens != decode tokens + sharded rows, `topk_tokens` not a multiple of `index_kpool`, chunks that do not tile the sharded rows, or a CUDA-graph capture. Every input is metadata that is identical on all ranks, so all ranks decide alike. The run-time verification is described under Numerics.
- **Numerics.** Bit-exact by construction. `_expand_pools_and_append_tail_kernel` is one program per (row, column tile) of integer arithmetic, and row r of its output depends only on `pool_ids[r]` and `seq_lens[r]`. The original expands row r on the rank that owns it and gathers the expanded rows (a byte copy); the compact path gathers the same pool rows (a byte copy) and expands each with the same positions through the same kernel. It is also checked at run time: the first three compact calls per process run the original path as well, into a scratch buffer, and compare with `torch.equal`. One MAX-reduce over the TP group's CPU (gloo) group makes every rank decide alike; on any mismatch every rank logs an ERROR, uses the original rows for that call and switches the compact path off for the rest of the process. The compact call peaks at about 14.3 KB per row (117.5 MB at 8,192 rows), inside the profiling reserve; the three verification calls peak about 67 MB above it, once per process (`VERIFY=0` removes that). CPU checks: 178 checks plus a 1,500-run random soak, 43 planted faults (all caught), and 56 shell scenarios.
- **Effect (v0.32.0, same prompts and tool, with vs without the patch).** Cold prefill, one user: 128k 3,134 -> 3,467 tok/s (+10.6 %), 256k 3,079 -> 3,450 (+12.0 %), 512k 3,013 -> 3,381 (+12.2 %), 1M 2,905 -> 3,257 (+12.1 %; time to first token 358.1 -> 319.3 s). At 8k and 32k, where no step is sharded, prefill is unchanged (3,361 / 3,460 vs 3,359 / 3,476 tok/s), and so is decode. The gathered output per indexer call drops from about 63 MB to about 15.7 MB, and every rank expands all rows once instead of its own share. On the boot that produced these numbers, the three verification calls reported `bitwise equal` and the compact path stayed active.
- **Upstream.** Not upstream: vLLM's exchange gathers the expanded ids. The patch changes only the payload of that exchange.

### 3.3 Tool-parser plugin

#### T1 — Tool-call grammar only when the client asks for one (`patches/plugins/glm45_auto_tool_parser.py`)

- **Problem.** vLLM v0.32.0 (#56403) made GLM-4.7/5.x tool calls grammar-constrained by default: the parser's strict level is FUNCTION, so every request that carries `tools` with `tool_choice: auto` is decoded under an xgrammar structural tag, even when no tool is strict. With MTP on this setup that costs most of the decode speed on agent turns. On the same 16 recorded agent turns (same seeds and cache salt, 256 output tokens): without a grammar, 79.9 tok/s median (acceptance length 2.69); with the default grammar, 9.2 tok/s median (acceptance length 1.54), about 8.7 times slower. With natural stops the median was 54.5 tok/s and the affected turns ran at about 8 tok/s. Step time rose from about 34 ms to 120-140 ms, roughly independent of acceptance.
- **Why, as far as we know.** Structured outputs do not turn off async scheduling, CUDA graphs or the drafter, but every constrained decode step goes through the engine's deferred-sampling path: an extra blocking RPC for the draft ids, CPU-side draft validation and bitmask building on the engine-core main thread, and a late sampling launch (which in the V2 runner also contains the MTP propose). Drafts are rejected wherever the grammar is active. Why that costs 90-100 ms here is not established; candidates are xgrammar's cost for large tool sets on GB10's host CPU, the extra RPC across the multi-node executor, and thread contention. The upstream PR measured no change on its own hardware. The thinking section is not constrained, because the prompt ends with `<think>` and `--reasoning-parser glm45` is set.
- **Change.** `Glm45AutoToolParser` subclasses vLLM's GLM-4.7 tool parser and sets `default_tool_strict_level = None`, which restores the pre-v0.32 default: a grammar is attached only when the client asks for one. Output parsing is unchanged. It registers as `glm45_auto` and logs `[recipe-plugin] tool parser glm45_auto registered ...`.
- **Switch.** `--tool-parser-plugin /opt/recipe-patches/plugins/glm45_auto_tool_parser.py --tool-call-parser glm45_auto` in place of `--tool-call-parser glm45`. From the first vLLM release that contains #61328, `--tool-strict-level auto` gives the same behaviour without a plugin; in v0.32.0 an explicit `auto` is a no-op, because the parser's default replaces it. `VLLM_ENFORCE_STRICT_TOOL_CALLING=0` removes every GLM tool grammar, including those for forced calls (which can then come back as plain content), so it is not used.
- **Numerics.** None: the plugin only decides whether a grammar mask is applied.
- **Effect (v0.32.0).** The same 16 turns with the plugin and natural stops: 79.87 tok/s median, acceptance length 2.79, the same speed as with no grammar.
- **What still gets a grammar.** A grammar is still attached, and decoding is slow in the same way, for `tool_choice: required` or a named function, for any tool with `"strict": true`, for `parallel_tool_calls: false`, and for `response_format` or structured-output requests. A request with `tool_choice: none`, or without tools, never gets a tool grammar (with `tool_choice: none`, tool calls arrive as raw content).
- **Hazard.** `include_reasoning: false` makes vLLM treat reasoning as already ended, so a request that also gets a grammar (see above) is constrained from the first token. The grammar's text rule excludes `</think>`, so the model could not close its thinking section under it. We found this by reading the code and have not reproduced it. With the plugin only the grammar cases above are exposed; without it, every request that carries tools (except `tool_choice: none`) is.
- **Upstream.** #56403 (v0.32.0) introduced the default; #61328 (merged on main after v0.32.0) lets an explicit `--tool-strict-level auto` win.

## 5. Replaced by configuration or upstream features

Four patches of the previous base are replaced by an upstream feature or a setting, and the recipe adds one environment variable that v0.32 makes necessary.

### 5.1 009 — keep the last prefix-cache block under MTP: `disable_eagle_block_drop`, not enabled

The old patch stopped vLLM from dropping the last matched prefix-cache block when MTP is on. vLLM treats MTP like EAGLE drafting and applies the EAGLE last-block rule, so every prefix hit lost one 1,280-token block: short prompts lost almost all reuse, and warm agent turns paid about 0.6 s more TTFT. Upstream turned this into a setting, `speculative_config.disable_eagle_block_drop` (#53388, v0.30.0), and flags the MTP draft KV group positionally (#55390, v0.31.0), so the old workaround of treating every group as a draft group is gone.

This release leaves the setting at upstream's default (off: the trailing block is dropped), pending a fresh correctness check of prefix reuse with MTP on v0.32. The upstream issue #53912 (prefix cache with MTP on hybrid models can corrupt output) was still open at the time of writing. To enable it, add `"disable_eagle_block_drop": true` to `--speculative-config`. On the previous base the old patch cut agent TTFT p50 from 1.28 to 0.88 s for one user (-31 %) and from 2.00 to 1.15 s for four agents, with decode unchanged; this release has not re-measured that.

### 5.2 024 — thinking-off requests: upstream parser fix plus the recipe's chat template

On the previous base, requests with `chat_template_kwargs {"enable_thinking": false}` (or `{"thinking": false}`, or `reasoning_effort: "none"`) returned the reasoning in `message.content`, followed by the answer, with an empty `reasoning` field. The model's chat template never reads `enable_thinking`: it always ends the prompt with `<think>`, so the model always reasons. And the `glm45`/`glm47` parser assumed the GLM-4.x contract, in which a false flag closes the think block in the prompt. Upstream fixed the parser side in #56994 (v0.32.0): for a GLM-5.3 always-think template, `Glm47MoeParser` ignores `thinking` and `enable_thinking`, so a thinking-off request parses like a default one (reasoning until `</think>`, then content and tool calls).

The recipe keeps its `--chat-template` file, `patches/files/p024_glm53_chat_template.jinja`. It is the model's own template except that thinking-off selects "Reasoning Effort: Low" instead of Max; every other request renders byte-identically. vLLM passes the command-line template to the renderer but does not replace the tokenizer's own template, which the parser inspects, so the two compose. The "Low effort" design follows kindlingai/glm-5.3-flash-gx10's notes (re-derived, not copied). Two small behaviours of the old patch are not carried: with `include_reasoning=false` and a JSON-type grammar (json, json_object, choice) the old patch returned the JSON as content; and it kept merging inline system messages on `/v1/messages` despite `--chat-template`, where upstream changed how that is detected.

### 5.3 030 — KDA chunk metadata on the host: FlashKDA prefill

On the previous base, KDA chunked prefill passed only the device tensor `cu_seqlens` to FLA's `chunk_kda_with_fused_gate`, which derived its chunk map on the device with `.tolist()` and blocking copies: 3 host syncs per prefill step, 9 with MTP verify rows. Patch 030 built that metadata on the host; it changed no speed in isolation and was an enabler for concurrency and long prompts.

In v0.32.0, FlashKDA, a fused CUDA prefill kernel (#55737, v0.30.0), is the default KDA prefill backend on SM12x when the shapes qualify (bf16, head_dim 128, bounded gate), and that path does not use FLA's chunk-index derivation. The recipe therefore drops 030 and relies on the default. The model code selects the backend silently, with no log line, so we checked it in a running rank-0 container: the layer's own selection function, given this model's configuration (head_dim 128, gate lower bound -5.0, bf16) on capability 12.1, returns `flashkda`. `--additional-config '{"kda_prefill_backend": "flashkda"}'` turns a silent fallback to the Triton chunk path into a boot error, and the launcher's readiness rules fail the boot on `no kernel image`. The move to FlashKDA is itself a numerics change against the previous base: a different kernel, with fp32 recurrent state in both.

### 5.4 031, core mechanism — upstream's TP-sharded indexer prefill

The old 031 contained its own sharding code, boot self-test and fingerprint. v0.32.0 contains the mechanism (#54951): `balanced_prefill_row_shard` splits the rows by indexer work, `PrefillRowShard` narrows each rank's share, and the group exchanges the selected ids with `all_gatherv`. Patch 031 now only moves upstream's gate from a row count to a depth test (section 3, patch 031). Compared with the old patch, upstream balances the split by work instead of cutting equal 16-row-aligned pieces, gathers the expanded ids instead of the pool ids (patch 035 undoes that), and has no boot self-test.

### 5.5 `VLLM_ALLREDUCE_USE_FLASHINFER=0` — added

v0.29.0 flipped the default of this variable from false to true (#52998). For a multi-node TP group the only FlashInfer backend allowed is MNNVL, which needs NVSwitch multicast (absent on GB10) and is untested over RoCE here. Setting `VLLM_ALLREDUCE_USE_FLASHINFER=0` keeps the all-reduce on NCCL, the path 012 hooks and every measurement in this file used. Check: `Using ['PYNCCL'] all-reduce backends (in dispatch order) for group 'tp:0'`. A `FLASHINFER` in that list means the variable did not reach the worker, and `Failed to initialize FlashInfer Allreduce` fails the launcher's readiness check.

## 6. Considered and not shipped

- **4-bit (NVFP4) weights or routed experts.** Declined for quality. A microbenchmark of 4-bit routed experts ran at 0.52-0.62 x the FP8 time (about 5.2 ms less per batch-1 decode step), but uncalibrated round-to-nearest NVFP4 had 0.169 relative RMS error on layer outputs. The recipe stays on the checkpoint's FP8; a change has to be lossless or at the level of patch 033.
- **A DFlash2 drafter.** The previous base carried two patches for it (hidden-state capture and the drafter itself), switched off. Measured there with a 3.1 B-parameter, 8-layer drafter at k = 3, single-user decode was 23 % slower than MTP with one draft token (33.94 vs 44.26 tok/s), because the drafter's own all-reduces at TP=8 lengthen the step. v0.32.0 supports DFlash2 drafters natively (#56983, #60763), but this recipe uses MTP only and the drafter weights are not part of it. A drafter would have to avoid cross-node collectives to pay off.
- **A copy-draft speculator.** A suffix-match ("copy") speculator was simulated on 64 recorded agent turns: an oracle gain of +5.2 %, and between -1.5 % and +2.2 % once the MTP draft prefill and async-scheduling costs are modelled. Not built.
- **Acceptance-adaptive draft depth** (the old 018 part B). It raised acceptance length by 17-20 % but not decode speed (chat -2.2 % and -4.5 %, agent contexts +1.4 % and +1.2 %, n.s.), because the deeper step costs more than assumed. Likewise three draft tokens at batch size 1: acceptance length +22-24 % but about 7.8 ms more per step (chat -5.7 % and -1.7 %, agent contexts -0.8 % and -1.8 %). Both measured on the previous base.
- **Deterministic KV order** (the old 023). It made greedy runs on short prompts reproducible by sorting each row's KV order, at a cost of 2-3 % of prefill, and prompts of 6.6k tokens and more stayed non-deterministic because of exact ties at the indexer's top-k boundary. It was an evaluation aid, not a serving feature, and is not carried.
